# Figures

Figures in this repository are **computed from parameters**, not drawn by hand and not
generated by an image model. This document explains why, and how to add one.

## The problem

Early attempts to produce an equatorial ring station diagram used text-to-image models.
Roughly twenty attempts across several prompting strategies, including deliberate
gamification intended to shake the model off its priors, produced two recurring failure
modes:

1. **Halos.** A ring rendered as a glowing annulus around the planet: a decorative shape
   at an arbitrary radius, with no relationship between the ring, the planet's surface,
   and the altitude the ring is meant to occupy.
2. **Plausible-looking infographics.** Diagrams with the visual grammar of engineering
   documents — callout lines, labels, tick marks, numbers — where none of the
   annotations correspond to anything. Confidently formatted, entirely uninformative.

This is not a prompting skill issue and better prompts will not fix it.

A diffusion model samples from the distribution of images that resemble the prompt. It
has no representation of an orbital radius, a tether attachment point, or the
relationship between altitude and orbital velocity. "Equatorial ring station" resolves
to _pictures of ring-shaped things near planets_, because that is genuinely what the
training distribution contains. Asking for dimensional accuracy asks the model for a
property it does not have.

The failure mode matters more than the inconvenience. A halo is obviously wrong and gets
discarded. **A plausible-looking infographic is wrong in a way that survives review**,
and in a research context that is the more expensive error.

## The solution

An orbital ring is parametric geometry. Every element follows from a small number of
physical quantities:

- planet radius
- ring altitude
- tether count and spacing
- the display exaggeration applied to make the altitude legible

So the figure is generated by code from a JSON parameter file. The geometry is computed,
the annotations are attached to computed positions, and the exaggeration factor is
printed on the face of the figure so nobody mistakes it for a scale drawing.

```bash
# render every figure
python tools/figures/ringgen.py --all

# verify committed figures still match their parameters (what CI runs)
python tools/figures/ringgen.py --all --check
```

Standard library only. No dependencies, no network, deterministic byte-for-byte output,
so a figure change shows up as a reviewable diff.

## What this buys

- **Correct by construction.** The ring cannot be at the wrong radius, because the
  radius is computed from the altitude rather than chosen for composition.
- **One-line revisions.** Changing the ring from 300 km to 2,000 km is an edit to one
  number, not twenty more prompts and a fresh set of hallucinated callouts.
- **Consistency across figures.** Every figure derived from the same parameters agrees
  with every other one. Prompted images never do.
- **Reviewable history.** A diff on a parameter file states exactly what changed. A diff
  on a raster image states nothing.
- **A CI guarantee.** The `figures` job regenerates from parameters and fails if a
  committed SVG has drifted. A figure in this repo is always what its parameters say it
  is.
- **Honest scale.** The exaggeration factor is rendered into the image, so the figure
  cannot be quoted out of context as a scale drawing.

## Where image models are still the right tool

This is an argument about engineering figures, not about generative imagery in general.
Concept art, mood boards, illustrative scenes, the donkey itself — all reasonable uses.
The line is whether the image is meant to carry dimensional information. If a reader
could measure something off it, it should be computed.

### Non-claims

Explicitly, what the current figure does **not** establish:

- It is a **schematic**, not a design. No structural, thermal, or power analysis informs
  it.
- Ring altitude is **exaggerated 9.2×** for legibility. A true-scale 300 km ring around
  a 6,371 km planet sits at 1.047 planet radii and renders almost against the limb.
- The mass stream is drawn as a single circle. Real proposals involve counter- rotating
  streams, magnetic coupling to a stationary sheath, and stability considerations that
  are not depicted.
- Tether count and spacing are illustrative, not derived from any load case.
- It does **not** depict a trajectory, a payload path, a launch sequence, or any moving
  vehicle. The tethers are structure under tension, not a route. The only element in
  motion is the mass stream, and it circulates rather than going anywhere. This one is
  here because a reader who knows the domain read the radial lines as a flight path, so
  the omission is demonstrably not obvious.
- Nothing here has been checked against a physical model. The parameters are render
  inputs, not engineering outputs.

A note on that second-to-last point, because it generalises. The figure was
geometrically correct, its labels pointed at real elements, and it still taught the
wrong mechanism to someone who knows this material. That is a third failure mode,
distinct from the two above: not a halo, not a fabricated infographic, but an accurate
drawing that a reader completes incorrectly. Computing a figure from parameters prevents
the first two. It does not prevent the third. Only review by someone who did not build
it does, which is the argument for stating non-claims on the page rather than trusting
the drawing to speak.

## Adding a figure

1. Add a parameter file under `tools/figures/params/`. Include a `meta.output` path and
   a `meta.description` that will become the SVG `<desc>`.
2. If the figure needs geometry `ringgen.py` cannot express, add a builder rather than
   hand-editing the output. Anything hand-edited will be overwritten by the next run and
   will fail the CI check.
3. Run `python tools/figures/ringgen.py --all` and commit both the parameter file and
   the generated SVG.
4. Add a row to the table above and a non-claims note if the figure implies anything
   quantitative.

## Conventions

- **SVG, not raster.** Text stays selectable, scaling is lossless, and diffs are
  meaningful.
- **Self-contained background.** Figures carry their own dark panel so they read
  correctly on light and dark documentation themes.
- **`role="img"` with `<title>` and `<desc>`** on every figure, for screen readers.
- **No random seeds.** Star positions and similar decoration are fixed in the parameter
  file, so output is byte-stable.
